# Workflow

## How the build works

```
extract/<your dump>.nds
        |  dsd rom extract
        v
extract/ATOJ/            arm9.bin, arm7.bin, overlays, files, banner
        |  dsd init  (once)
        v
config/ATOJ/             delinks.txt, symbols.txt, relocs.txt per module
        |  dsd delink
        v
build/ATOJ/delinks/      relocatable objects, one per translation unit
        |  mwccarm (C/C++ sources)  +  delinked objects (everything else)
        v
build/ATOJ/arm9.o        linked with the LCF generated by dsd lcf
        |  dsd rom build
        v
tennis_ATOJ.nds          compared against the base ROM
```

A module is matching when the linked output is byte-identical to the
corresponding region of the base ROM. `ninja check` reports this per module and
`ninja sha1` verifies the rebuilt ROM as a whole.

## The decompilation loop

1. Pick a function. Open `objdiff.json` in objdiff, or run `ninja dis` and read
   `build/ATOJ/asm/`. Small leaf functions are quick to match and they show you
   the compiler's idioms early.
2. Carve out a translation unit by adding an entry to
   `config/ATOJ/arm9/delinks.txt` for the function's address range:

   ```
   src/arm9/code_02012345.c:
       .text start:0x02012345 end:0x020123a8
   ```

   `dsd` derives the delinked object path from the source path, so the file name
   is where the decompiled code will end up.
3. Write the C in `src/`, with shared types in `include/`. The compiler gets the
   game version through `-d ATOJ`, and each file is compiled as C or C++ based
   on its extension.
4. Compare with `ninja check` or objdiff and keep iterating on the C until the
   object matches.
5. Commit the C and the `delinks.txt`/`symbols.txt` changes together so the
   build stays reproducible.

Once a file matches, mark it `complete` in `delinks.txt`; `dsd lcf` then links
your object instead of the delinked assembly.

## Symbols

`symbols.txt` gives addresses their names:

```
func_02012345 kind:function(arm,size=0x30) addr:0x02012345
data_020ab123 kind:data(word[4]) addr:0x020ab123
```

Naming a function makes its assembly and relocations readable. After a file
matches, `ninja apply` copies sizes and local/global information from the linked
ELF back into `symbols.txt`.

Two `dsd` helpers are worth knowing:

* `dsd sig list` / `dsd sig apply` find and rename library functions by
  signature, which identifies known SDK routines in the ROM.
* `dsd diff new` / `dsd diff apply` compare symbol configuration between two
  versions of the project.

## Matching tips

Retail's game code came from one CodeWarrior build, `1.2/b56` (build 56,
`Runtime Built: Sep 16 2004`): it rebuilds the whole ROM to the digest with no
per-file overrides, and it is `DEFAULT_MWCC_VERSION` in `tools/configure.py`.
Later service packs such as `1.2/sp2` are still on disk, but they are not the
default and are not the expected answer to a stubborn function. If one unit has
evidence of a different origin, sweep `--mwcc-version` for that unit, confirm the
full digest still matches, and record the tag in `config/ATOJ/mwcc_versions.txt`
rather than changing the default.

`CC_FLAGS` mirrors the standard DS release configuration (`-O4,p -proc arm946e
-interworking -enum int`). One changed flag changes every file, so change them
deliberately.

Matching `.rodata`/`.data` often means writing declarations in the same order as
the original; the delinks ranges tell you how large each object was.

`ninja objdiff` writes decomp.me scratch metadata (compiler `mwcc_30_131`, the
project's C flags), and you can export context for the scratch with the
project's includes.

One function per commit keeps the diff reviewable and makes a regression easy to
bisect.

## Data units

A data unit is a delinks entry with a `.data` (or `.rodata`) range plus a `.c` file that
declares the object, for example

```
src/arm9/data_02042240.c:
    complete
    .data       start:0x02042240 end:0x02042264
```

```c
#include "types.h"

u32 data_02042240[9] = { 1, 2, 3, 4, 5, 6, 8, 9, 10 };
```

`dsd` then emits `data_02042240.o(.data)` between the surrounding gap objects in the LCF, so the
bytes land at the original address; `ninja sha1` proves it. Two things to remember:

* `build.ninja` is only regenerated when `tools/configure.py` or `dsd.exe` changes, so after
  adding a source run `python tools/configure.py ATOJ` (or delete `build.ninja` and re-run
  configure) before `ninja`. Skipping this fails the link with
  `Specified file ...data_02042240.o not found`.
* `tools/match/progress.py` counts a pure data unit as a complete unit but not as a function;
  keep that distinction if you touch the aggregation.
